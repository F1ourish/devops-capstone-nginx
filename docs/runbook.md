# Runbook

## Назначение

Этот документ описывает базовые операционные действия для работы с сервисом Nginx в текущей версии проекта.

Он используется как практический runbook для запуска, остановки, перезапуска, проверки состояния, базовой валидации конфигурации и отработки типовых сценариев отказа.

Для быстрых проверок состояния и первичной диагностики следует использовать `docs/observability.md`.

## Предварительные условия

Перед выполнением действий из этого документа предполагается, что:

* Docker и Docker Compose установлены и доступны в системе
* проект открыт в корректной директории репозитория
* файл compose.yaml находится в актуальном состоянии
* конфигурация Nginx и связанные файлы не содержат непроверенных изменений
* пользователь выполняет команды из корня репозитория

## Основные операционные действия

### Сборка и запуск сервиса

Команда: `docker compose up -d --build`

Назначение:

* собрать актуальный образ
* запустить сервис в фоне
* применить изменения в конфигурации и Docker-слое

### Остановка сервиса

Команда: `docker compose down`

Назначение:

* остановить контейнеры проекта
* удалить контейнеры, созданные текущим Compose-проектом

### Перезапуск сервиса

Команда: `docker compose restart nginx`

Назначение:

* перезапустить сервис `nginx` без полной пересборки

### Просмотр состояния контейнера

Команда: `docker compose ps`

Назначение:

* проверить, что контейнер запущен
* увидеть текущее состояние сервиса
* подтвердить отсутствие Exited или restart loop

### Просмотр логов

Команда: `docker compose logs nginx`

Назначение:

* посмотреть ошибки запуска
* проверить runtime-сообщения сервиса
* получить первичную информацию о причине сбоя

### Просмотр последних строк логов

Команда: `docker compose logs --tail=50 nginx`

Назначение:

* быстро посмотреть последние события без полного вывода логов
* использовать при точечной диагностике после недавних изменений или сбоя

### Проверка конфигурации Nginx

Команда: `docker compose exec nginx nginx -t`

Назначение:

* проверить валидность конфигурации Nginx в запущенном контейнере
* убедиться, что конфигурация не содержит ошибок

### Проверка конфигурации Nginx, если контейнер не запущен

Команда: `docker compose run --rm nginx nginx -t`

Назначение:

* проверить конфигурацию Nginx без использования `exec`
* использовать этот способ, если контейнер находится в состоянии `Exited` или ещё не запущен

### Проверка итоговой конфигурации Compose

Команда: `docker compose config`

Назначение:

* проверить итоговую Compose-конфигурацию
* убедиться, что файл `compose.yaml` и связанные параметры валидны

### Проверка основного endpoint

Команда: `curl -i http://127.0.0.1:8080/`

Назначение:

* проверить доступность основного HTTP endpoint
* убедиться, что сервис отдаёт ожидаемый ответ

### Проверка health endpoint

Команда: `curl -i http://127.0.0.1:8080/healthz`

Назначение:

* проверить доступность технического health endpoint
* убедиться, что сервис возвращает ожидаемый health-ответ

## Базовый порядок проверки после изменений

После внесения изменений рекомендуется выполнять следующий минимальный набор проверок:

1. Проверить итоговую конфигурацию Compose
Команда: `docker compose config`
2. Проверить конфигурацию Nginx
Команда: `docker compose exec nginx nginx -t`
3. Пересобрать и запустить сервис
Команда: `docker compose up -d --build`
4. Проверить состояние контейнера
Команда: `docker compose ps`
5. Проверить основной endpoint `/`
Команда: `curl -i http://127.0.0.1:8080/`
6. Проверить health endpoint /healthz
Команда: `curl -i http://127.0.0.1:8080/healthz`
7. При необходимости проверить логи
Команда: `docker compose logs nginx`

## Действия при типовых ситуациях

### Сервис не отвечает по HTTP

Рекомендуемый порядок действий:

1. Проверить основной endpoint `/`
Команда: `curl -i http://127.0.0.1:8080/`
2. Проверить health endpoint `/healthz`
Команда: `curl -i http://127.0.0.1:8080/healthz`
3. Проверить состояние контейнера
Команда: `docker compose ps`
4. Проверить логи контейнера
Команда: `docker compose logs nginx`
5. Проверить конфигурацию Nginx
Команда: `docker compose exec nginx nginx -t`

### Контейнер завершился после запуска

Рекомендуемый порядок действий:

1. Проверить состояние контейнера
Команда: `docker compose ps`
2. Проверить логи контейнера
Команда: `docker compose logs nginx`
3. Проверить конфигурацию Nginx через `run --rm`
Команда: `docker compose run --rm nginx nginx -t`
4. Проверить итоговую конфигурацию Compose
Команда: `docker compose config`
5. После исправлений повторно запустить сервис
Команда: `docker compose up -d --build`

### Изменения внесены, но результат не соответствует ожиданиям

Рекомендуемый порядок действий:

1. Проверить, что изменения сохранены в нужных файлах
2. Проверить итоговую конфигурацию Compose
Команда: `docker compose config`
3. Проверить конфигурацию Nginx
Команда: `docker compose exec nginx nginx -t`
4. Повторно пересобрать и запустить сервис
Команда: `docker compose up -d --build`
5. Проверить HTTP-ответы и логи
Команды:
* `curl -i http://127.0.0.1:8080/`
* `curl -i http://127.0.0.1:8080/healthz`
* `docker compose logs nginx`

# Failure drills

## Drill 1. `/healthz` недоступен

Сценарий:

* основной сервис может продолжать отвечать на `/`
* health endpoint `/healthz` недоступен или возвращает неожиданный ответ

Цель:

* подтвердить, что проблема ограничена health endpoint
* отработать базовый порядок диагностики от внешнего симптома к конфигурации

Шаги:

1. Проверить основной endpoint `/`
Команда: `curl -i http://127.0.0.1:8080/`
2. Проверить health endpoint `/healthz`
Команда: `curl -i http://127.0.0.1:8080/healthz`
3. Проверить состояние контейнера
Команда: `docker compose ps`
4. Проверить логи контейнера
Команда: `docker compose logs nginx`
5. Проверить конфигурацию Nginx
Команда: `docker compose exec nginx nginx -t`

Ожидаемый результат:

* причина сбоя локализована на уровне endpoint, логов или конфигурации
* зафиксирован воспроизводимый порядок проверки

## Drill 2. `/` недоступен

Сценарий:

* основной endpoint `/` недоступен или возвращает неожиданный ответ
* при этом `/healthz` может работать корректно

Цель:

* отличить сбой основного маршрута от общего отказа сервиса
* проверить внешний и внутренний сигналы состояния

Шаги:

1. Проверить основной endpoint `/`
Команда: `curl -i http://127.0.0.1:8080/`
2. Проверить health endpoint `/healthz`
Команда: `curl -i http://127.0.0.1:8080/healthz`
3. Проверить состояние контейнера
Команда: `docker compose ps`
4. Проверить логи контейнера
Команда: `docker compose logs nginx`
5. Проверить конфигурацию Nginx
Команда: `docker compose exec nginx nginx -t`

Ожидаемый результат:

* подтверждено, затрагивает ли проблема только основной маршрут или весь сервис
* определён следующий шаг диагностики или исправления

## Drill 3. Контейнер переходит в `Exited` после запуска

Сценарий:

* после `docker compose up -d --build` контейнер не остаётся в состоянии `Up`
* сервис завершается вскоре после запуска

Цель:

* отработать диагностику сбоя процесса внутри контейнера
* закрепить различие между `exec` и `run --rm` для проверки конфигурации

Шаги:

1. Проверить состояние контейнера
Команда: `docker compose ps`
2. Проверить логи контейнера
Команда: `docker compose logs nginx`
3. Проверить конфигурацию Nginx без `exec`
Команда: `docker compose run --rm nginx nginx -t`
4. Проверить итоговую конфигурацию Compose
Команда: `docker compose config`
5. После исправлений повторно запустить сервис
Команда: `docker compose up -d --build`

Ожидаемый результат:

* установлена причина завершения контейнера
* подтверждено, что после исправлений контейнер остаётся в состоянии Up

## Drill 4. Ошибка конфигурации после изменения Nginx

Сценарий:

* после правки конфигурации Nginx проверка `nginx -t` завершается с ошибкой
* сервис может не запускаться или работать некорректно

Цель:

* отработать безопасную проверку конфигурации до и после перезапуска
* закрепить важность config validation перед эксплуатационными действиями

Шаги:

1. Проверить конфигурацию Nginx
Команда: `docker compose exec nginx nginx -t`
2. Если контейнер не запущен, выполнить альтернативную проверку
Команда: `docker compose run --rm nginx nginx -t`
3. Проверить итоговую конфигурацию Compose
Команда: `docker compose config`
4. Исправить конфигурацию и повторить проверку
5. Пересобрать и запустить сервис
Команда: `docker compose up -d --build`
6. Выполнить базовые HTTP-проверки
Команды:
* `curl -i http://127.0.0.1:8080/`
* `curl -i http://127.0.0.1:8080/healthz`

Ожидаемый результат:

* конфигурация проходит проверку без ошибок
* сервис успешно запускается и отвечает ожидаемым образом

## Drill 5. После изменения сервис запущен, но результат не соответствует ожиданиям

Сценарий:

* контейнер находится в состоянии `Up`
* конфигурация формально валидна
* HTTP-ответы или поведение сервиса не соответствуют ожидаемому результату

Цель:

* отработать post-change validation
* закрепить проверку не только статуса контейнера, но и фактического поведения сервиса

Шаги:

1. Проверить основной endpoint `/`
Команда: `curl -i http://127.0.0.1:8080/`
2. Проверить health endpoint `/healthz`
Команда: `curl -i http://127.0.0.1:8080/healthz`
3. Проверить состояние контейнера
Команда: `docker compose ps`
4. Проверить логи контейнера
Команда: `docker compose logs nginx`
5. Проверить конфигурацию Nginx
Команда: `docker compose exec nginx nginx -t`
6. При необходимости повторно пересобрать и запустить сервис
Команда: `docker compose up -d --build`

Ожидаемый результат:

* подтверждено фактическое состояние сервиса после изменения
* найдено расхождение между ожидаемым и реальным поведением
